# Week 6 卫星项目：基础 RAG Agent

> **一句话卖点：可溯源 RAG + 诚实拒答**

第 6 周周末项目（详细拆解见 `../week6-daily-plan.md`）。检索→拼上下文→生成全链路，检索能力后续并入主线「备忘录检索」（V3 D7）。

## 功能

- **检索→拼上下文→生成**：问库里有答案的问题，基于检索结果回答并**附来源**
- **诚实拒答**：资料中没有相关信息时，直接说"不知道"，不编造
- **30 条测试用例**：正常问答 10 + 拒答场景 10 + 溯源要求 10，跑出通过率基线

## 运行步骤

## 架构

```
用户提问 → embedding → Chroma 检索 Top-K → 拼 <context> 上下文
        → LLM 生成（要求只基于上下文）→ 回答 + 附来源（metadata）
        → 相关度过低 → 诚实拒答
```

### 两道拒答防线（设计要点）

「诚实拒答」不是靠一句 prompt，而是**两道独立防线**，判据不同、失败模式也不同：

| | 防线① 检索层 | 防线② 生成层 |
|---|---|---|
| **谁判** | 代码 | 模型 |
| **判据** | 相似度数字（`1 - distance < SIM_THRESHOLD`） | prompt 里的指令 |
| **时机** | 调 LLM **之前** | 调 LLM **之后** |
| **代价** | 便宜（省一次 LLM 调用） | 贵（已付费） |

为什么必须有防线②：**生成层对代码不可见**——模型想拒答，代码无从得知。
故用 `response_format={"type": "json_object"}` 把回答约束成结构化契约
`{"found": bool, "answer": str}`，让「模型的拒答」变成一个**代码可读的布尔值**。

### 契约违约的两种形态（都必须处理）

| 形态 | 表现 | 走到哪 | 处理 |
|---|---|---|---|
| **JSON 坏** | 解析抛异常 | `except` 分支 | 拒答 + stderr 留痕 |
| **JSON 合法但字段缺失** | **不抛异常** | `try` 正常结束 | **必须自己判**（`"found" not in data`） |

**安全默认必须往「拒绝」倒**：`data.get("found", False)` —— 而非 `True`。
字段缺失说明模型没守契约，此时**默认判「有答案」= fail-open = 放行幻觉**。
取舍很明确：**诚信事故（编造答案）比可用性事故（多拒一次答）严重得多**。

### 日志信道

内部诊断信息一律走 **stderr**（`file=sys.stderr`），stdout 只留用户可见的回答与来源。
判据一句话：**这条信息是给谁看的？** 用户 → stdout；开发者 → stderr。
